# Support Center: local native plugin

Support Center 0.3.0 is a host-reviewed native functional plugin, not downloaded JavaScript. Its frontend manifest and PL/EN/DE translations live in `apps/frontend/src/plugins/support-center`; backend registration and reviewed migrations live in `apps/backend/src/plugins/support-center`. Shared contracts are in `packages/types/src/plugins` and `packages/types/src/support-center`. Business logic, API adapters, components, hooks, preview fixtures and tests remain in their own module folders.

## Source ownership and distribution

The official native source package is maintained in `Tyravex/tyravex-plugins`, under `integrations/support-center`. The panel keeps an integrated compilation copy; shared contracts stay in `packages/types/src/support-center`. The package includes reviewed source files, migrations, PL/EN/DE resources and tests, with a `source-lock.json` checksum inventory and guarded synchronization scripts. Compare sources before editing or applying an update. The plugin repository's `native-plugins.json` lists native sources separately from installable language/theme ZIP packages in `registry.json`.

Source synchronization does not execute migrations, install dependencies, start processes or change Git state. It requires compatible host integration and refuses conflicting local files. Publishing the native source does not enable dynamic installation of arbitrary executable code through Marketplace; enabling/upgrading the compiled plugin still uses the panel's existing confirmed native installer. Older published panel revisions may not contain the required host integration.

## Preview before publishing

### Reliability and retention 0.3

Existing installations require an explicit update: open the local Support Center card in Plugins or Marketplace, choose **Update local plugin**, and confirm `tyravex.support-center`. The transaction applies missing reviewed migrations through `004_reliability`, verifies migration checksums and preserves enabled/disabled state. Viewing the card never runs database changes. New installations include all four migrations. Until upgraded, operational views show an upgrade requirement; the database-free preview remains available. Applying an update changes the panel database and requires the operator's authorization.

Public mutations use a shared `mutations` module. The API accepts an optional UUID `Idempotency-Key`; the frontend supplies it and reuses it on manual retry after a network error or uncertain 5xx response. Matching retries return the original acknowledgement without inserting another message, grant or notification. Reusing the key with a different payload is a conflict. Receipts last 24 hours and store acknowledgement metadata and a request fingerprint, never message bodies, file contents or access reasons. Indexed cleanup removes at most 100 expired receipts per keyed mutation. This contract does not automatically retry agent operations.

Database-backed per-account limits work across API processes: 5 new tickets per 10 minutes, 20 public replies or notes per minute each, 15 status/assignment/decision changes per minute each, and 6 access requests/direct grants per minute combined. HTTP 429 includes `Retry-After` and a localized error code. Idempotent replays do not consume another allowance. Failed domain mutations roll back their counter change; attempts rejected by the rate limit remain counted. Both new tickets and reopening enforce the existing 20-active-ticket capacity under an account-scoped capacity lock, including concurrent changes on different services.

Status transitions are centralized: OPEN/IN_PROGRESS can be resolved or closed, RESOLVED can be reopened or closed, and CLOSED must be reopened before handling. Repeating the existing status does not add history or notifications. Reopening never revives old service-access consents.

The `notifications` module records typed events with ticket ID and service name/ID. Socket delivery occurs after the mutation commits; a socket failure cannot undo the mutation. Messages from clients notify the eligible active assignee first, falling back to the active ticket-handling queue. Role membership alone without read/manage permissions is insufficient. New tickets use the queue; assignment, status and consent events have distinct titles in PL/EN/DE. Stored notifications remain available through refresh, reconnect and window focus. Open conversations and unread counters also invalidate their queries on live notification delivery. Socket delivery is best effort; this version does not add a separate retry worker or promise exactly-once transport.

Deleting a service now archives its tickets instead of cascading away conversations. Reviewed migration 004 adds service identity snapshots, nullable live-service references and a plugin-owned trigger on `public.Service`. Deletion closes tickets, revokes pending/active consents and records an archival event. The original ticket owner retains read access only if they still owned the service at deletion; deleting a transferred service does not restore access to a previous owner. Staff history preserves the existing internal-note policy. Archived tickets cannot be reopened, assigned, replied to or used for service access. Account deletion retains the existing account-level cascade policy. Keeping plugin data on uninstall also keeps archival behavior; explicit plugin-data removal removes the owned trigger/functions before dropping only plugin objects.

### Ticket workflow

Staff can claim an unassigned open ticket or transfer it to an eligible active staff account. Claiming also moves an open ticket into IN_PROGRESS in the same transaction. Concurrent claims serialize. Closed tickets keep their assignee for history but cannot be reassigned. An author with both support:read and support:manage can handle their own ticket; this does not grant access to internal notes or allow self-approved service access. Ordinary owners remain limited to client actions.

Public replies have per-account read markers and unread menu badges. Waiting state depends on the latest public reply. Filters include service, status, assignee, search and unread replies. Opening a conversation marks only the displayed public message range as read. Internal notes do not notify clients or change public waiting state; both messages and note events are excluded server-side from client views, including privileged ticket owners.

Service owners see active support consents directly on the service with scopes, expiry countdown, ticket link and revocation. Workspace audit entries track request ID, operation and pending/success/failure/unknown outcome with sanitized error codes. They never store file contents or secrets. Agent timeouts are unknown outcomes because completion cannot be guaranteed.

Run `node apps/backend/scripts/test-support-workflow-database.cjs` only with authorization for a disposable Docker PostgreSQL test and a short-lived loopback HTTP server. It requires Docker and the cached PostgreSQL image; it uses a unique owned container and a separate temporary database, not the panel configuration. The HTTP phase binds only to `127.0.0.1`, uses real JWT/session validation and closes the server before cleaning up the owned container. Its workspace adapter is a controlled test double; this is not a real-agent installation or file-write test.

Open **Administration → Plugins → Marketplace → Local plugins → Preview**, or `/admin/plugins/local/support-center/preview` with `plugin:read`. The interactive preview uses in-memory sample data and supports client/staff perspectives, messages, ticket state, consent, revocation and history. Reset or reload discards preview changes. It never calls the support API or agent.

The local card is also available on the Plugins page. It is explicitly marked unpublished. No commit, release or public catalog entry is required to view it.

## Explicit local installation

`GET /admin/local-plugins` only reads registration metadata. `POST /admin/local-plugins/tyravex.support-center/install` requires `plugin:read`, `plugin:manage`, and an exact plugin ID confirmation. It runs reviewed static migrations and plugin registration in one PostgreSQL transaction, protected by a lifecycle advisory lock. Failure rolls back schema changes and registration. The database role needs DDL privileges. Migration checksums prevent silently changing a previously applied migration.

Only installation creates `plugin_support_center`, containing migration history, tickets, messages, grants and events. No support tables are added to the core Prisma schema, no application startup hook runs DDL, and no user-provided SQL or schema name is executed. Core User, Service, Permission, Role, Plugin and Notification records are reused. Creating a PostgreSQL schema provides logical separation; it is not a security sandbox for arbitrary plugin code.

Installation adds `support:read`, `support:manage` and `support:access` permissions and grants all three to system-managed Owner. It creates an unassigned `Support` role template containing only read and ticket-management permissions, without service access. Existing roles with that name are preserved without any permission or membership changes. Staff role assignment and service-access permission remain explicit administrator actions. User-side ticket access is based on current service ownership, without a global support role. Installed routes are `/support` for clients and `/admin/support` for staff. Sidebar links appear when the plugin is active. The installer refreshes the current account's permissions after a successful install.

Disable uses the standard plugin lifecycle and permanently revokes existing pending/active consents. Roles and memberships are preserved; only plugin capabilities become inactive. Other permissions on a mixed role remain usable. Role forms show a dedicated Support Center group with enabled/disabled status; administrators can still edit assignments while the plugin is disabled. Re-enabling does not reactivate prior service consents. Uninstall is available from the local card only after disabling. The administrator explicitly chooses whether to retain data or drop the owned schema. Reinstallation never revives old consents. Generic ZIP uninstallation cannot touch native plugin storage.

## Authorization and scope

Temporary service access supports two consent flows. Staff with support:read and support:access can request selected scopes and duration; the owner approves or rejects the request. Alternatively, the current service owner can use **Grant access to assignee** without a prior request. This explicitly creates an active grant for the displayed ticket assignee, with the selected scopes and 15–240 minute duration. The server checks current ownership, open ticket state, matching assignee, an active recipient account and its access permissions. A changed assignee, self-grant or duplicate pending/active grant is rejected. Both paths use the same execution checks and revocation controls; direct consent has a distinct audit event with the recipient name. No new schema migration is needed.

The default plugin Support role contains ticket read/manage permissions only. If an assignee cannot receive temporary access, the UI explains the missing support:access capability and administrators can open that worker's roles. Enable support:access in an appropriate role, assign that role, and refresh permissions. The service owner can then grant access or approve the worker's request. Owner consent does not grant global account permissions automatically.

Tickets are service-bound. Staff read, reply/manage and temporary access permissions are separate. Staff cannot approve their own access; only the current service owner can approve or reject a request. Owner or requesting staff can revoke it. Duration is 15–240 minutes starting at approval. Closing/resolving a ticket revokes its requests. Expiry is checked at execution time rather than relying on a background task. Current service ownership is checked again, so a service transfer invalidates old consent.

The first workspace supports runtime status, file listing, UTF-8 file reading and revision-checked file editing. Separate scope is required for known secret-file paths such as `.env`, hidden paths and keys. Source code may also contain secrets: file-read consent is meaningful access, not a guarantee of secret-free files. Status-only access excludes application logs. Console commands, power actions, backups, archive extraction and unrestricted administrative access are not exposed by this initial scope.

The existing workspace broker validates consent in its service transaction, binds the grant and original owner in encrypted request metadata, and rechecks it before agent dispatch. The API rechecks consent after agent completion before releasing data. Revocation cannot undo a command that the agent has already started, but prevents subsequent commands and release of private read results. Existing agent protocol is reused.

## Ticket interface

The customer queue is `/support`; the staff queue is `/admin/support`. Each ticket has a separate conversation route at `/support/tickets/:ticketId` or `/admin/support/tickets/:ticketId`. The queue uses compact status filters, searchable rows, service/assignee filters and page navigation. Filters and pagination are stored in the URL and restored by the conversation's back link. Existing `?ticket=` links redirect to the conversation route.

Staff can switch between the full-width list and an inbox with inline ticket selection. Inbox selection and layout are reflected in the URL. Modified clicks on ticket links still open the separate conversation. The client layout keeps the list and conversation separate.

The conversation has a main message/history area and a right panel for the service, assignee and temporary access. Details start collapsed on smaller screens. Staff workspace tools have a separate tab and remain unavailable without an active grant. Both owner consent flows use the existing backend checks. Archived tickets keep their conversation and history without write controls. Switching between conversation and history preserves the reply draft; hidden conversations do not mark incoming messages as read. Changing ticket or preview actor resets the draft. Ticket pages fetch their detail without downloading the queue or service selector.

The local Marketplace preview supports both perspectives and layouts without API calls or database writes. All interface labels are bundled in the plugin's PL/EN/DE resources.

## Plugin-owned languages

The service workspace header exposes **Request support** to the current owner while Support Center is enabled, including before environment installation. It opens the shared ticket form with the service name and ID locked to the displayed service, then navigates to the new conversation. It uses the existing owner-checked ticket endpoint and does not request or approve any service-access grant. Submission errors preserve the draft message.

The namespace is exactly `plugin.tyravex.support-center`. Bundled resources are registered independently of the panel's `translation` namespace. They follow the selected UI language with English fallback. They neither require German language-pack updates nor override panel strings. Preview resources remain available when the plugin is uninstalled; operational routes and data access remain disabled.

## Validation and limits

Unit and HTTP tests cover permission separation, owner transfer, expiry, revocation, agent dispatch, secret paths, installation confirmation, migration checksums, retention choice and namespace isolation. Preview tests prove that backend APIs are not called. The workflow integration test has passed against an explicitly approved, disposable PostgreSQL container. It covers upgrades, concurrency, pagination, private notes, read markers, revocation, retained-data reinstallation and plugin-only removal. The test removes its own container and never uses the panel database. A separately approved real-agent test on 2026-11-22 also passed installation, actual file read/write, both consent flows, scope isolation, expiry and revocation. Its temporary accounts/service/container/volume/state were removed; see `docs/support-center-validation-2026-11-22.md` for boundaries and additional installation/RBAC findings.

Queues use filtered page pagination (up to 50 entries per page); messages and events use stable cursors (up to 50 entries per request). Support Center is bundled native code in this development phase. Publishing arbitrary third-party functional ZIP plugins, installing executable code, sandboxing, and automatic native-plugin upgrades are not enabled by the existing language/theme Marketplace installer. They require a separate deployment contract and review before public release.

## Managed role ownership and upgrades

The core RBAC catalog may already contain a Support role without plugin permissions. Its name, role protection, and account membership alone do not enable ticket handling. The local plugin card reports whether both support:read and support:manage are present. **Enable ticket handling for role** requires the exact role ID confirmation and plugin/role management permissions. It adds only those two permissions, protects the role, preserves all existing permissions and memberships, and records an audit event. It refuses a role configured as the default for new accounts. It never grants support:access.

Assign the prepared role from **Users → selected account → Roles** using role:assign. Users with role:manage but not role:assign cannot assign accounts. The staff queue links to user management, and role assignment shows a warning if Support is missing ticket permissions. Open sessions refresh account permissions on window focus or using **Refresh permissions** in the staff queue. Late refresh responses cannot restore a signed-out account or replace another signed-in user.

New installations apply `002_managed_roles` in the plugin schema and bind only a newly created Support role by its ID. Existing roles with the same name are not adopted automatically. Role reads return ownership and current plugin status; protected roles show plugin/protection badges, and disabled-plugin annotations. The RBAC API blocks deletion and renaming while the plugin remains installed, including DISABLED status. Permission edits and memberships remain independent.

For a local installation prepared before this metadata existed, open the Support Center card, choose **Link and protect role**, and confirm the exact role ID. This explicit operation applies the reviewed metadata migration if missing, preserves all permissions and memberships, and records an audit event. It requires both plugin management and role management, plus their read permissions. Merely viewing roles or the card never upgrades the database or assumes ownership from a name. The metadata table is retained with plugin data when requested on uninstall; protection ends once the plugin is unregistered.
